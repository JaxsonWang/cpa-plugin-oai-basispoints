# v0.1.20 凭据级 WS 开关验测

## 范围与结论

2026-09-27（UTC+8），在 v0.1.19 基础上补充 CPA 凭据 `websockets` 开关判断。只修改本插件，不修改 CPA 主程序或用户运行中的配置，也不替用户开启任何凭据。

用户要求的 CPA 日志级别调整已取消：曾在本地 CPA 工作区新增的两份日志辅助文件已撤回，没有修改既有 CPA 文件。宿主 `openai_responses_websocket_forward.go` 发出的 INFO 日志不会因为替换本插件 SO 而改变。`invalid client tool relay` 的 422 仍表示工具数据校验失败，本版不降低校验标准，也不将其伪装成成功。

## 两层开关

| 插件设置 | 当前凭据 `websockets` | 实际行为 |
| --- | --- | --- |
| `auto` | 明确开启 | 优先尝试一次 WS 握手，默认上限 5 秒 |
| `auto` | 关闭 | 直接 HTTP/SSE，握手次数为零 |
| `auto` | 缺失、null、无效值 | 直接 HTTP/SSE，握手次数为零 |
| `http` | 任意值 | 直接 HTTP/SSE，不握手 |

有效值遵循 CPA 的布尔解析约定，支持布尔值和可解析布尔字符串；不会把任意非空字符串、数字 1 等当作开启。先读取 CPA `AuthAttributes` 的有效值，再读取 `AuthMetadata`；只有元数据中没有该字段时才读取源 `StorageJSON`。例如当前属性或元数据为 false、旧源数据为 true，仍然禁止 WS，不能被旧文件快照重新开启。

虚拟认证创建和刷新都保留该开关。插件只读取源凭据，不写回 OAuth JSON，不修改原生 Codex 记录的开关，也不添加另一个重复的凭据级配置项。

**本地开关开启只允许尝试 WS，不代表 Basis Points 保证支持该次握手。** 允许尝试后，v0.1.19 原规则继续适用：连接未建立的网络/握手失败可回退一次 HTTP；401/403/407/429 不回退；已建立有效连接后的断流、发送异常、超时或协议错误不重放；取消和插件停用不启动回退。下一独立请求重新按其当前凭据开关判断。非流式 HTTP 保留原 JSON/SSE 解析语义。

## 用户替换 v0.1.19 后的线上检查

在用户指定的 Chrome 管理页面读取，确认插件生效版本 **0.1.19**、配置为 `auto`、握手上限 5 秒、Responses 地址为默认 Basis Points 地址。旧 SO 文件名中含 `v0.1.10`，但管理页面实际注册版本是 0.1.19，不能仅按文件名判断未更新。

定向真实检查共 **12 次 HTTP 请求：10 次 200、2 次预期 400、零意外 5xx**。覆盖模型能力、流式/非流式正文、命名空间函数和 36 行密集引号/反斜杠 custom 补丁、工具结果往返、参数拒绝后继续可用，以及直接流式时序。

32 行正文产生 **384 个 delta**：首段约 **5.809 秒**，完成约 **8.697 秒**，首段提前约 **2.888 秒**。这是一次现场样本，证明兜底链路仍增量交付，不是速度保证或统计基准。

同时，线上日志持续出现：

```text
Basis Points WS fallback to HTTP: reason=handshake_rejected status=404 handshake_attempts=1
```

隔离的诊断动态库在本机、使用匹配线上所选身份的授权凭据，捕获到上游 404 正文：

```json
{"detail":"Responses websocket transport is not enabled."}
```

该诊断构建只在忽略的 `build/live-validation-v0.1.19/` 中增加脱敏诊断，不交付、不覆盖原库，也不修改正式源代码。同一身份的其他直接握手探测也出现过 101；后续控制压缩开关的四次直接探测均为 101，因此**不能把一次 404 推断为固定的账号权限、压缩扩展或 NAS 网络问题**。插件实际部署路径的 WS 仍未证实成功，业务通过主要证明 HTTP/SSE 兜底可用。

最初的两个凭据对照仅提示可能有关；在同一凭据也能取得 101 后已撤回“固定账号不支持”的归因。完整根因仍未确定，不增加未经证实的协议伪装或探测重试。本次新门槛是用户明确要求的本地策略修正，不声称它能替上游开启 WS。
