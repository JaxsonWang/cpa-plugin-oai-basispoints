# 双账号 WS 本地修订与验测

> 本文保留 v0.1.20 本地诊断阶段的记录；后续源码以 v0.2.0 发布。发布不代表两个真实账号的上游 WS 均已成功，发布版本的验证见 [v0.2.0](v0.2.0.md)。

日期：2026-09-27，UTC+8。仅本地修改和打包；没有提交、推送、发布或修改 NAS。

## 修订结论

- 撤回 `http_only_auth_ids` 及其配置元数据、状态字段和按账号强制 HTTP 的实现。此前该参数只是避开失败账号的 WS，并没有实现两个账号都使用 WS，不再作为本问题的解决方案。
- `upstream_transport: auto` 下，两个账号分别使用自己的 CPA 凭据；各自的 `websockets` 明确开启才允许握手，没有单账号数量限制，不根据会话 ID 换账号。
- 每轮按原设计只尝试一次握手；未建立连接的 404、网络错误或握手超时可回退原 HTTP/SSE。401/403/407/429 不回退，WS 已连接后不跨传输重放请求。没有新增重试、冷却或记住失败账号的逻辑。
- 不改 CPA 主程序、源 OAuth 文件、认证调度、工具中继或既有取消/超时语义。工作区原有 README 修改保留。

## 真实上游握手边界

使用用户此前授权的本地 OAuth 凭据，账号仅记为 A/B，不保存到源码或在报告中披露 token、完整账号 ID。

2026-09-27 15:44–15:47 的受控对比仅握手，成功后进行 Ping/Pong 或关闭连接，没有发送生成请求：

| 条件 | A | B |
| --- | --- | --- |
| 原请求头，重复 2 次 | 101 × 2 | 404 × 2 |
| 增加 CPA 原生使用的 `OpenAI-Beta: responses_websockets=2026-02-06`，重复 2 次 | 101 × 2 | 404 × 2 |
| Go 客户端，开启压缩 | 101 | 404 |
| Python 客户端，关闭压缩 | 101 | 404 |
| Python 客户端，deflate 压缩 | 101 | 404 |

B 的响应均明确为 `Responses websocket transport is not enabled.`。在请求正文、`task_id` 和 `turn_id` 发送前已经被拒绝，因此本次证据不支持“两个账号对不上会话 ID”是这些 404 的原因；补协议头或改变压缩也未解决。

这只能确定本次 B 凭据请求受到上游 WS 开关拒绝，不能据此推断其永久账号权限、套餐、地区或具体服务端灰度规则。历史其他样本曾出现不同结果，不能宣称 B 永久不支持 WS。此前线上个别握手超时是另一类故障，不能仅凭状态 0 的回退日志定位到 DNS/TCP/TLS/Upgrade。

**两个真实账号都成功 WS 直连的目标尚未完成。** 本轮撤回错误的手动分流，不把 HTTP/SSE 回退包装成 WS 修复，也不加入实测无效的协议头或压缩变更。
