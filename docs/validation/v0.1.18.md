# v0.1.18 正文增量流式与部署验收

## 结论和范围

2026-09-26（UTC+8），先完成正文增量交付实现和本地验证，生成 Linux amd64 `.so` 候选。当时按要求仅本地交付，没有推送或发布。用户随后确认替换 `.so`，同日真实部署复验通过；按用户“通过后提交并发布”的授权进入 v0.1.18 发布流程，最终发布构建及资产状态以 GitHub Actions/Release 为准。未代替用户远程更换服务端文件。

修改前：插件读取完整上游响应、解析和校验后，才统一回放正文。修改后：取得有效响应、消息和内容片段身份后，按上游正文 delta 交付；完整终态仍是工具整批校验及最终用量、完成状态的依据。没有延时拆字或人为动画。

## 实现和错误边界

- `streaming.go` 管理异步读取、响应尺寸/超时检查、上游关闭和活动流生命周期；RPC 返回后仍保留活动流，停用时取消上游并等待工作协程结束。
- `stream_events.go` 管理消息与内容索引、逐段正文、事件顺序及终态补全；终态必须与已交付文本一致，不重复输出已有正文或完成事件。
- 工具名称和参数不提前发给客户端。只有完整终态通过原有工具目录、参数 schema、call ID、并行调用约束等整批校验后，才交付工具。
- **未开流**的非法工具保留原有最多一次重生成；最终校验失败仍以 422 返回，不改原有非流式语义。
- **已交付正文**后出现非法工具、上游失败或截断，保留已经发送的正文，发送明确的协议 `error` 并结束传输；该流不再重跑，不发送成功终态，也不交付半批工具。HTTP 状态已经是 200，不能再改成 422/502。
- CPA v7.3.17 的 `host.stream.close.error` 只有字符串、没有结构化状态；业务失败改由协议事件传递，避免该字符串被误当成普通 500。原版宿主转换为 Claude SSE 后，错误也必须被客户端识别，不能仅以 HTTP 200 判断成功。
- 一次性 JSON、没有可提前交付消息生命周期的响应或仅有终态的 SSE，仍只能在完整响应就绪后交付；这由实际上游数据决定，不伪装成逐字流。
- 客户端自行重连或另发请求不是插件同一请求内的重生成，不能承诺插件可阻止这些独立请求。

### Claude 客户端独立回退的实测边界

Claude Code 2.1.247 收到流式错误后，即使设置了测试用的 `CLAUDE_CODE_MAX_RETRIES=0`，仍会另发一个非流式请求：

- 坏工具夹具：首个流式请求调用上游一次、不重生成；客户端另发非流式请求，该请求按既有规则重生成一次，合计三次上游调用，最终客户端明确失败。
- 截断夹具：首个流式请求调用一次；客户端另发非流式请求再次失败，合计两次调用，最终客户端明确失败。
- 通过上游 `stream` 标志、重生成提示和 CPA HTTP 日志确认，这不是插件重复已交付的同一个流。不修改客户端的既有回退行为，也不增加跨请求缓存去阻断新请求。另发的非流式请求仍遵循既有错误/凭据处理语义。

验测初始断言将上述行为误当成插件重试；查明请求归属后改为分别检查每一请求，保留原失败日志。另修正了仅存在于测试脚本的 Codex inline map 配置错误，以及 app-server 尚未退出便清理临时 HOME 的竞态；最终相应检查通过，未通过吞掉错误或修改生产实现来回避验测。

## 同夹具延迟对比

在同一本机使用 v0.1.17 和 v0.1.18 原生动态库：上游首段在约 50ms 后可读，再等待约 600ms 才发送终态。相同消息生命周期和正文下，记录从请求开始到客户端首个正文 delta：

| 正文字符数 | v0.1.17 首段 | v0.1.18 首段 |
| --- | ---: | ---: |
| 128 | 660.25ms | 55.75ms |
| 8,192 | 663.64ms | 58.61ms |
| 65,536 | 670.95ms | 58.01ms |

新实现均在终态前约 604–605ms 交付首段；旧实现均在 EOF 后才交付。这证明移除了插件等待完整响应造成的首段延迟，**不是生产速度承诺、网络压测或上游首字优化**。仍需真实上游按增量发送，代理/客户端也不能再次整段缓冲。

## WebSocket 支持的三个边界

| 链路或服务 | 当前证据 |
| --- | --- |
| 客户端 → CPA | 使用现有 CPA 凭据完成 WebSocket `101` 升级，发送 `response.create`，收到四个正文 delta 和 `response.completed`，结果为 `WS_TRANSPORT_OK`。本项是 50 次 HTTP 之外的额外真实推理验测 |
| 本插件 → Basis Points | 代码通过 `host.http.do` / `host.http.do_stream` 向 `https://bps.openai.com/basispoints/api/responses` 发 HTTP POST；非流式解析 JSON/SSE，流式按 SSE 增量处理。没有实现或声明上游 WebSocket 传输 |
| Basis Points 自身是否另有可用 WS | 对同一路径的直接 WS 握手返回 **401**，不是“不支持 WS”的证明。没有直接上游 OAuth 凭据的认证验测，无法确认其 WS 接口契约，也不能断言它只支持 SSE |

[OpenAI 官方 Responses WebSocket 文档](https://developers.openai.com/api/docs/guides/websocket-mode)明确介绍公开 Responses API 的 WS 模式，但这不能直接证明 Basis Points 接口拥有相同支持。现有插件无需把上游换成 WS，已经能够持续交付正文；客户端使用 WS 也不意味着插件到上游使用 WS。

WS 探测最初因本机 Python 默认 CA 路径为空而无法校验证书；改用已安装 certifi 的受信 CA 后完成以上探测，**没有关闭 TLS 验证**。原始与修正后的探测结果均保留。

## 升级和未验证项

升级时先备份服务器旧包，替换 `.so` 并重启 CPA，确认实际加载 `0.1.18`；同一插件目录不要放两个相同插件 ID 的库。GitHub Release 不会自动替换已加载的服务端动态库。六平台正式发布包由 CI 重新构建，其哈希应以 Release 随附的 `checksums.txt` 为准，不能套用上述本地 Zig 包的哈希。

本机为 macOS：本地实际加载的是同源码 macOS 动态库；Linux `.so` 完成交叉编译、ELF/符号及哈希验证，本机未直接运行 Linux 加载测试。用户更新后的真实服务已通过前述功能及增量时序验测，但未独立读取远端二进制哈希，未人工查看桌面逐字显示或完成长期压力测试。Fast、独立 compact、ID 续接、多代理 v2、结构化输出、verbosity 映射及 OAuth 刷新同步等既有能力边界未改变。
