# v0.1.17 密文代理契约修正与部署验收

## 结论与发布状态

2026-09-26（UTC+8），部署后的 v0.1.16 在多代理 v2 验收中出现可复现的子代理 502。故障证据与差分诊断见 [v0.1.16 验收报告](v0.1.16.md)。该候选没有满足“验测无问题后发布”的条件，因此未提交、推送、打标签或发布 GitHub Release。

v0.1.17 针对该问题重新构建，采用新版本号避免与旧二进制混淆。用户报告替换新包后，2026-09-26（UTC+8）的真实部署复验通过；按用户授权进入 GitHub 发布流程，发布构建及资产校验仍以实际 Actions/Release 结果为准。

## 修正范围

- 撤回插件别名的 `multi_agent_version` 和 `multi_agent_reasoning_effort` 声明，不将规范模型的原生消息加密能力当成中继已经实现的能力；其他提供商的模型元数据不变。
- 对 `agent_message.content[]` 中的 `encrypted_content` 提前返回 `400 unsupported_encrypted_agent_message`。验证发生在上游调用之前，错误不包含消息内容；不解密、不改成普通正文、不吞掉输入。
- 既有 reasoning 密文和纯文本代理消息保持原样；继续保留已经完成真实验测的补丁能力、时钟、异步提问和既有工具中继。
- 不修改个人客户端配置、协议转换回退、凭据冷却逻辑、历史身份回放或其他已关闭问题对应的机制。多代理 v2、`text.verbosity` 的真实上游映射仍未实现，不能宣称这些能力已经修好。

2. 当前完整源码的干净副本通过 `go test -race -count=1 -json ./...`：379 项测试/子测试通过，零失败；正式源码包与测试均未排除。
3. `go vet ./...`、`go mod tidy -diff`、gofmt、actionlint 和 `git diff --check` 通过。源码副本用于避开原工作区忽略目录中的历史测试残留，未删除这些残留。
4. 原版 CPA v7.3.17 实际加载同源码 macOS arm64 动态库，76 项 HTTP/CLI 检查通过；含新密文输入的流式/非流式 400、零上游调用、不泄露内容，以及同一凭据后续正常请求成功。推理上游为明确的合成夹具。
5. 桌面内置 Codex `0.158.0-alpha.2` 实际执行新增/修改/删除三个临时文件的原生补丁，收到一个完成的 `fileChange` 和三次 `turn/diff/updated`，文件内容及聚合 diff 正确。
6. 同一客户端实际执行时钟、休眠、异步提问；三个父工具各执行一次，测试程序实际回答后答案进入上下文。通过真实客户端工具目录检查，v2 专用工具不再暴露。此项亦使用合成上游，不冒充生产验收。
7. 已构建源码的 33 个 Go/模块文件哈希与当前工作区一致。Linux 产物通过 ELF64 x86-64、共享库类型、插件入口导出和符号版本检查；仅依赖 `GLIBC_2.2.5` / `GLIBC_2.3.2` 版本符号。

## 发布与升级边界

生产替换由用户执行，本轮未远程操作服务器。升级时应备份原动态库，替换并重启 CPA、确认实际加载版本；同目录不要保留两个同 ID 插件。

Codex 应刷新模型目录并开启新会话，避免旧会话继续保留 v2 模式。本次客户端验测使用服务实时目录与新会话；已完成补丁/差异事件、时钟/异步输入、格式与密文拒绝、Claude 工具往返及凭据可用性检查。发布 Release 不会自动替换服务端动态库。

GitHub Actions 沿用六平台构建；成功后还需核对全部发布资产、校验和、归档内容、平台架构及内嵌版本。正式发布包由 CI 重新构建，不能把本文中本地 Zig 验测包的哈希当成所有发布包的哈希，应使用 Release 随附的 `checksums.txt`。

没有人工检查桌面可视差异面板或执行长期压力测试；只对上述明确覆盖的行为给出通过结论，不宣称所有客户端场景及尚未实现的能力均可用。
